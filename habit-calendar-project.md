## 1. Идея

Календарь привычек для себя.

Требования:
- Десктопное приложение под **Windows**. В будущем синхронизация с мобильным приложением на **Android**.
- Основное окно: метрики и таблица «все привычки × дни месяца/недели и т. д.», в каждой ячейке отметка о выполнении.
- Всплывающие уведомления Windows с напоминаниями о привычках.
- Иконка в трее. По клику открывается **основное приложение** на экране «Сегодня», где можно отметить выполнение. Слева вкладки: настройки, метрики и т. д. (вместо маленького отдельного окна, как у Steam/Discord).

---

## 2. Принятые решения

- **GUI: Wails** (выбран вместо Fyne). Версия 3, см. раздел 3.
- Привычки только вида «сделал / не сделал» (без счётчиков и длительности).
- **У каждой привычки своё расписание**: каждый день, через день, по дням недели и т. д.
- **Архивация вместо удаления**, история сохраняется.
- Можно отмечать выполнение **за прошлые дни**.
- **Настраиваемое время начала нового дня** (например, отметка в 01:00 может относиться к вчерашнему дню).
- Хранение: SQLite.
- Синхронизация позже, через сервер на Go (это совпадает с моим планом изучения REST API).

## 3. Технологии

### Wails
- Нужна именно **третья версия** (v3): в v2 нет трея. В v3 есть система трея, в том числе всплывающее окно из трея с автоскрытием.
- На момент 13.11.2026 v3 в стадии **бета** (3.0.0-beta.2, август 2026). API заявлен как стабильный, но это пререлиз: в документации и примерах возможны расхождения.
- Команда называется `wails3`, а не `wails`. Не смешивать гайды для v2 и v3.
- Логика на Go, интерфейс на HTML/CSS/JS (понадобится немного фронтенда).
- В журнале изменений упоминается упаковка под Android. Насколько это зрелая возможность, не проверено, поэтому на неё пока не рассчитываем (мобильное приложение, возможно, будет делаться отдельно).
- Перед началом этапа с GUI стоит заново проверить актуальный статус Wails v3.

### SQLite
- Драйвер `modernc.org/sqlite`: чистый Go, не требует C-компилятора.
- Удобнее JSON для запросов по датам и метрик.

## 4. Что надо продумать (замечания и «мелочи»)

### Модель данных
Это самое важное: интерфейс легко переделать, а миграция данных болезненна.
- Расписание: каждый день, через день, по дням недели. Для «через день» нужна точка отсчёта (дата начала привычки).
- Чем считать пустую ячейку: «пропуск» или «сегодня не нужно». Это зависит от расписания.
- Привычки не удаляются, а архивируются.
- Даты хранить как **день** (`2026-11-13`), а не как момент времени, чтобы не было проблем с часовыми поясами.
- Решить, как отметка около полуночи привязывается к дню (настройка начала дня).
- Что делать с отметкой, если привычку потом заархивировали.
- У каждой записи **уникальный ID** (лучше UUID, не автоинкремент) и поле `updated_at`. Это обязательно для синхронизации.
- Запись об отметке однозначно определяется парой «привычка + день». Повторная отметка того же дня не должна создавать дубль.

### Метрики
- Текущая и лучшая серия (streak).
- Процент выполнения за неделю и месяц.
- Тепловая карта.
- Логика серий с расписаниями содержит много граничных случаев, поэтому её нужно покрыть тестами.

### Напоминания
Работают, только пока приложение запущено. Поэтому нужны:
- автозапуск вместе с Windows;
- сворачивание в трей при закрытии окна;
- запрет второго экземпляра приложения;
- «отложить на N минут»;
- не напоминать о том, что уже отмечено;
- решение, что делать с напоминаниями, пропущенными, пока ПК спал или был выключен.

### Остальные мелочи
- экспорт/бэкап в CSV;
- начало недели (понедельник или воскресенье);
- тёмная тема;
- настройки.

### Синхронизация с Android (самая сложная часть)
Думать о ней нужно с самого начала, даже если делать позже.
- Нужен сервер (будущий REST API на Go) или синхронизация через файл в облаке.
- Приложение должно работать офлайн и синхронизироваться при появлении связи.
- Правило конфликтов: например, побеждает запись с более поздним `updated_at`.
- Удалённое помечать флагом, а не стирать физически, иначе удаление не передастся на другое устройство.
- Таблица «привычки × дни месяца» на телефоне не поместится, там нужен другой интерфейс. Поэтому ядро приложения нужно отделить от UI.

## 7. Текущее задание (этап 1)

Wails пока не нужен. Делаем пакет с логикой.

1. Создать модуль (`go mod init`) и пакет ядра, например `internal/core`.
2. Описать структуры `Habit`, `Schedule` и `Entry`.
3. Написать функцию «нужно ли выполнять эту привычку в этот день».
4. Написать функцию, превращающую момент времени в «день привычки» с учётом настройки начала дня.
5. В `main` вызвать всё это на нескольких примерах и вывести результат.

Вопросы, над которыми нужно подумать при проектировании:
- Как хранить расписания «каждый день», «через день» и «по дням недели» в одной структуре (тип расписания + параметры)? Откуда брать точку отсчёта для «через день»?
- Что однозначно определяет `Entry`? Что должно происходить при повторной отметке того же дня?
- Как хранить день: `time.Time` или строкой `2026-11-13`? Какие проблемы даёт первый вариант?
- Что делать с отметками архивированной привычки?
- Какие поля нужны заранее для синхронизации (ID, `updated_at`)?

Дальше: после первой версии разобрать код и научиться писать тесты (пакет `testing`) для функций расписания.
